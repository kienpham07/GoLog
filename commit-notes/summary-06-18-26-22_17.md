## Overview

This commit completes the next backend step in the JWT authentication flow by adding reusable Gin middleware for bearer-token validation and applying it to the log retrieval endpoint. Before this change, the frontend could send a JWT to `/api/logs`, but the backend route did not enforce that token. After this change, `/api/logs` rejects requests that do not include a valid `Authorization: Bearer <token>` header.

The commit also makes repository-maintenance changes:

- `commit-notes/` is no longer ignored, so project documentation can be committed.
- Existing commit-note Markdown files are added to the repository.
- The accidental root-level React package files and committed root `node_modules/` tree are removed. The active Next.js frontend remains under `frontend/`, with its own `frontend/package.json` and `frontend/package-lock.json`.

The primary problem solved is server-side access control for reading parsed log data. The dashboard can no longer rely only on client-side redirects; the backend now validates the JWT before returning logs.

## Code Changes

### New Authentication Middleware

The new middleware lives in `backend/middleware/auth.go`:

```go
func AuthRequired() gin.HandlerFunc {
    return func(c *gin.Context) {
        authHeader := c.GetHeader("Authorization")
        if authHeader == "" {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "Authorization header missing"})
            return
        }

        parts := strings.Fields(authHeader)
        if len(parts) != 2 || !strings.EqualFold(parts[0], "Bearer") {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "Invalid token format"})
            return
        }

        token, err := utils.ValidateToken(parts[1])
        if err != nil || !token.Valid {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "Invalid or expired token"})
            return
        }

        c.Next()
    }
}
```

Important implementation details:

- The middleware checks for the `Authorization` header before any protected handler logic runs.
- `strings.Fields` is used to split the header, which tolerates extra whitespace better than a raw string split.
- The scheme check uses `strings.EqualFold`, so `bearer`, `Bearer`, or other casing variants are accepted.
- Invalid, missing, malformed, expired, or incorrectly signed tokens return `401 Unauthorized`.
- `c.AbortWithStatusJSON` prevents the protected endpoint from continuing after an auth failure.
- `c.Next()` is called only after token validation succeeds.

This is an architectural improvement because authentication is now reusable. Future routes can be protected by adding the middleware to the route declaration instead of duplicating token parsing inside each handler.

### Protected Logs Endpoint

`backend/cmd/main.go` now applies the middleware directly to the logs route:

```go
router.GET("/api/logs", middleware.AuthRequired(), func(c *gin.Context) {
    logs, err := database.GetLogs()
    // ...
})
```

This makes `/api/logs` the first backend route that is truly protected by JWT validation. The frontend work from the previous commit already sends the token with this request, so this backend change closes the gap between client-side authentication behavior and server-side enforcement.

### JWT Validation Helper

`backend/utils/jwt.go` now exposes:

```go
func ValidateToken(tokenString string) (*jwt.Token, error) {
    return jwt.Parse(tokenString, func(token *jwt.Token) (interface{}, error) {
        if token.Method != jwt.SigningMethodHS256 {
            return nil, jwt.ErrSignatureInvalid
        }
        return secretKey, nil
    })
}
```

The helper centralizes token validation next to token generation. It confirms that incoming tokens use the same HS256 signing method used by `GenerateToken`, then returns the initialized `secretKey` so `jwt.Parse` can verify the signature and registered claims such as expiration.

Because `utils.InitJWT()` is still called during application startup, validation depends on the existing `JWT_SECRET` environment variable requirement. A missing secret continues to be a startup-time failure instead of allowing weak token verification at runtime.

## Impact

- `GET /api/logs` now requires a valid JWT in the request header:

```http
Authorization: Bearer <token>
```

- Clients that call `/api/logs` without a token now receive:

```json
{"error":"Authorization header missing"}
```

- Clients that send an incorrectly formatted header now receive:

```json
{"error":"Invalid token format"}
```

- Clients that send an invalid, expired, or incorrectly signed token now receive:

```json
{"error":"Invalid or expired token"}
```

- The existing frontend dashboard should continue working because it already stores `golog_token` after login and sends it as a bearer token when fetching logs.
- Any manual API clients, scripts, or external consumers that previously called `/api/logs` anonymously must now log in first and include the returned token.

### Breaking Changes and Deployment Considerations

- **Breaking API behavior:** `/api/logs` changed from public to authenticated. Existing callers must be updated to send a bearer token.
- **Authentication prerequisite:** A user must register and log in through `/api/register` and `/api/login` before accessing logs.
- **Environment requirement:** `JWT_SECRET` remains required for backend startup because `utils.InitJWT()` initializes the signing key used by both `GenerateToken` and `ValidateToken`.

## Testing

Manual testing should cover:

- Start the backend with a valid `JWT_SECRET`.
- Register a user with `POST /api/register`.
- Log in with `POST /api/login` and confirm the response includes a token.
- Call `GET /api/logs` with no `Authorization` header and confirm it returns `401`.
- Call `GET /api/logs` with a malformed header, such as `Authorization: Token abc`, and confirm it returns `401`.
- Call `GET /api/logs` with an invalid bearer token and confirm it returns `401`.
- Call `GET /api/logs` with the token returned from `/api/login` and confirm it returns log data.
- Open the frontend dashboard after login and confirm it loads logs successfully.
- Let a token expire or manually alter it in browser storage, then confirm the frontend redirects back to `/login` after the backend returns `401`.

Recommended future automated tests:

- Unit tests for `utils.ValidateToken` covering valid tokens, expired tokens, wrong signing methods, and invalid signatures.
- Middleware tests for missing, malformed, invalid, expired, and valid bearer tokens.
- Integration tests for `/api/logs` to lock in the new authenticated behavior.
